Q1 . Import Mode loads data into Power BI’s in-memory storage, making reports and dashboards very fast, while DirectQuery keeps the data in the source database and queries it whenever the report is used. For real-time order tracking, I would recommend DirectQuery because new orders and delivery updates can be reflected without regularly importing the entire dataset, although performance depends on the database and network. For historical analysis, Import Mode is better because large amounts of historical data can be analyzed quickly using Power BI’s in-memory engine. The trade-off is that Import Mode requires data refreshes to get updates, while DirectQuery can provide fresher data but may be slower and place more load on the source database.

Q2 . 1.Remove blank rows first: In Power Query, I would use Remove Rows → Remove Blank Rows so empty records do not affect order counts or later transformations. This creates a consistent dataset before applying other cleaning steps.
2. Standardize city names: I would select the City column and use Transform → Format → Trim to remove extra spaces, followed by Capitalize Each Word (or another consistent casing method) so values like ahmedabad and Ahmedabad become Ahmedabad.
3. Split CustomerName and PhoneNumber: I would select the combined column and use Split Column → By Delimiter, choosing the hyphen (-) as the delimiter, creating separate CustomerName and PhoneNumber columns. Doing this in Power Query Editor is better than manually cleaning Excel because the steps are saved and automatically repeatable whenever new FoodRush data is loaded, making the reporting pipeline consistent and reducing manual errors.

Q3 . The Orders table should be the fact table because each row represents a food delivery order and contains measurable values such as TotalAmount. Customers and Restaurants should be dimension tables, connected to Orders using CustomerID and RestaurantID respectively. In Power BI Model View, I would create one-to-many (1:*) relationships from Customers[CustomerID] → Orders[CustomerID] and Restaurants[RestaurantID] → Orders[RestaurantID], with filtering flowing from the dimensions to the fact table. This Star Schema is more efficient for DAX because customer and restaurant information is stored once, reducing duplication and making measures such as total revenue, average order value, and revenue by city easier and more reliable to calculate.

Q4 . A Calculated Column is calculated row-by-row when the data is loaded or refreshed, so Quantity × UnitPrice produces a stored value for every order, while a Measure is calculated dynamically based on the current report context. For the total revenue KPI Card, a Measure is the correct approach because it should respond to slicers such as City; for example, Total Revenue = SUMX(Orders, Orders[Quantity] * Orders[UnitPrice]). When a City slicer is applied, Power BI changes the filter context, so the measure recalculates SUMX only for orders belonging to the selected city. The calculated column itself does not change because its row-level values were already calculated, whereas the measure's result changes dynamically with the selected filters.
